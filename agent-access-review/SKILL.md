# Ревью доступа агента

Промпт-инъекцию сейчас нельзя надёжно предотвратить. Значит, вопрос не «послушается ли агент злую инструкцию», а «что плохого он сможет сделать, если послушается». Этот скилл отвечает на второй вопрос.

## Что нужно на входе
- Системный промпт.
- Список инструментов агента: функции, MCP-серверы, вебхуки, доступы к БД и API — с описаниями и параметрами.
- Откуда агент получает текст: сообщения клиентов, сайт, документы, письма, результаты поиска, ответы других агентов.
- Куда агент может отправить данные: ответ клиенту, email, мессенджер, HTTP-запрос, запись в CRM.

Читай код и конфиги, если они есть, а не только описание: описание часто отстаёт.

## Шаг 1. Инвентаризация
Составь таблицу по каждому инструменту:

| Инструмент | Читает | Пишет / меняет | Необратимо? | Кто вызывает | Подтверждение человеком |
|---|---|---|---|---|---|

«Необратимо» — удаление, отправка сообщения наружу, платёж, отмена записи, изменение цены, публикация.

## Шаг 2. Источники текста
Пометь каждый источник:
- **доверенный** — написан вами или проверен человеком (материалы после проверки, промпт);
- **недоверенный** — всё, что может написать посторонний: сообщения клиентов, сайты, письма, отзывы, документы от клиентов, результаты поиска.

## Шаг 3. Опасные сочетания
Ищи агентов, у которых одновременно есть:
1. доступ к закрытым данным (база клиентов, внутренние документы, ключи);
2. недоверенный текст на входе;
3. способ отправить данные наружу (письмо, HTTP-запрос, ссылка с параметрами, ответ постороннему).

Все три сразу — **высокий риск**: инструкция из недоверенного текста может вынести закрытые данные. Два из трёх — отметь и проверь, не появится ли третье при следующей доработке.

Ещё отдельно отметь:
- необратимые действия без подтверждения человеком;
- инструменты с широкими правами (произвольный SQL, произвольный HTTP, доступ ко всей файловой системе);
- общие ключи: агент ходит в сервис с правами администратора, а не с ограниченным токеном;
- память или история, куда может попасть недоверенный текст и влиять на следующие диалоги.

## Шаг 4. Рекомендации
По каждому риску — конкретное изменение, в порядке предпочтения:
1. **Убрать доступ** — агенту он не нужен для задачи.
2. **Сузить** — только чтение, только своя таблица, фиксированный набор параметров вместо произвольного запроса.
3. **Разделить** — один агент читает недоверенный текст и не имеет доступа к данным; другой работает с данными и не видит недоверенный текст.
4. **Человек подтверждает** — необратимое действие только после «да» оператора.
5. **Логи и лимиты** — журнал вызовов, лимит вызовов на диалог.
6. **Промпт** — последним. Инструкция «не раскрывай данные» не защита, а дополнение.

## Шаг 5. Отчёт
Сохрани `access-review-<агент>-<дата>.md`: таблица инструментов, список источников, найденные сочетания с уровнем риска, рекомендации с приоритетом. В начале — 3 строки итога для того, кто не будет читать весь отчёт.

## Правила
- Не добавляй ключи, токены и реальные данные в отчёт — только названия и роли.
- Если что-то не удалось проверить по коду, так и напиши: «по описанию, не проверено».
